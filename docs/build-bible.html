Engineering & Product Blueprint

The AI-Automated Government Exam Portal

A single source of truth for Indian government-exam aspirants — every notification, date, vacancy, eligibility rule and result, scraped from official sources, verified by AI, and published automatically. This document is the build bible: 22 components, one coherent system.

The problem

Exam information is scattered across dozens of official sites and stale aggregators. Aspirants miss deadlines and trust the wrong sources.

The wedge

An exam-centric dashboard — timelines, days-left, eligibility, vacancy history and comparisons — that no incumbent does well, kept live by automation.

The moat

A self-updating data engine (scrape → AI extract → validate → publish) + programmatic SEO. Fresh, structured, trustworthy data compounds.

Product Constitution #

The constitution is the tie-breaker for every future decision. When two features conflict, these principles decide.

Mission

Help every Indian government-exam aspirant know exactly what to do next — never miss a date, never trust a wrong source, never feel lost — through information that is complete, correct, and always current.

Who we serve

Primary: aspirants aged 18–32 preparing for SSC, UPSC, Banking, Railways, State PSCs, Police & Teaching exams, mostly on mobile, often on modest data plans, comfortable in Hindi + English. Secondary: parents, coaching institutes, and search engines (a first-class “user”).

Principles (in priority order)

#PrincipleWhat it means in practice
1Accuracy over speedNever publish an unverified fact. The 90% gate is sacred. A wrong date is worse than a late one.
2Official-source anchoredEvery date/link shows its official source. We inform & link; we never impersonate a government body.
3Exam-centric, not notice-centricOrganise the world around the exam’s journey (timeline, stages, days-left), not a reverse-chron list of notices.
4Mobile-first & fastSub-2.5s LCP on a mid-range phone. Works on 3G. Every KB counts.
5Automation-first, human-gatedMachines do the toil; humans approve the grey zone. The system scales content without scaling headcount.
6SEO is a product surfaceStructured data, clean URLs and freshness are features, not afterthoughts.

Non-negotiables (guardrails)

  • No fact goes live below the confidence threshold without human approval.
  • Every published entity keeps a version history and its source document.
  • Clear disclaimer + official link on every page; no government insignia/impersonation.
  • User eligibility data is private (RLS), never sold, used only to personalise.

North-star & guardrail metrics

North star: weekly aspirants who complete a “next action” (viewed a live deadline / applied via official link / set an alert). Guardrails: data-accuracy rate (audited sample), time-from-official-update-to-live, and organic sessions.

Database Design #

A production-grade Postgres schema ships alongside this document (schema.sql + seed.sql), already tested end-to-end on Postgres 16. It has 25 tables across three domains, plus read-model views, full RLS, and a search index.

A · Content domain

conducting_body, exam, exam_cycle, exam_stage, key_date, vacancy, eligibility, cutoff, official_link, update_feed, article, exam_relation

B · Pipeline domain

source, scrape_run, raw_document, extraction, validation, content_version, publish_event

C · User domain

profile, user_follow, subscription, notification, notification_delivery, push_subscription

Design decisions worth keeping

  • Evergreen vs time-bound split — exam ↔ exam_cycle (unique on exam_id, year). Dates/vacancy/cutoffs hang off the cycle.
  • Structured + flexible — hot fields are real columns (fast filters for the eligibility engine & “days left”); the long tail lives in jsonb (rules, meta).
  • Pipeline is data — every published fact traces to an extraction → raw_document → source. Auditable by construction.
  • Everything versioned — content_version stores a JSON snapshot + diff per change → powers “what’s changed”, rollback, audit.
  • Security by default — RLS: content is world-readable only when published_at is set; user tables are owner-only; pipeline tables are service-role-only.

Core relationships (abridged DDL)

create table exam_cycle (
  id            uuid primary key default gen_random_uuid(),
  exam_id       uuid references exam(id) on delete cascade,
  slug          text unique,          -- 'ssc-cgl-2026'
  year          int,  status cycle_status,      -- enum: application_open…
  total_vacancy int,  published_at timestamptz,  -- null = draft (hidden by RLS)
  unique (exam_id, year)
);
-- key_date drives "days left"; is_deadline flags feed the countdown
create view v_cycle_next_deadline as            -- next upcoming deadline per cycle
  select c.slug, k.label, (k.event_on - current_date) as days_left …
VerifiedThe shipped schema was executed on Postgres 16 with a realistic SSC-CGL-2026 seed: the days-left view returned 12, the timeline ordered correctly, full-text search matched “income tax”, and eligibility matching (age 25 + graduate) returned true. Run schema.sql then seed.sql in the Supabase SQL editor to reproduce.

URL Structure #

URLs are permanent public contracts and a top SEO lever. Design them once, keep them forever, and make them human-readable and keyword-rich.

Page typePatternExample
Conducting body/{body}/ssc
Exam hub (evergreen)/{body}/{exam}/ssc/cgl
Exam cycle (dashboard)/{body}/{exam}-{year}/ssc/cgl-2026
Sub-view/{body}/{exam}-{year}/{view}/ssc/cgl-2026/vacancy
Compare/compare/{examA}-vs-{examB}/compare/ssc-cgl-vs-ssc-chsl
State/state/{state}/state/madhya-pradesh
Calendar/calendar · /calendar/{year}/{month}/calendar/2026/08
Article / guide/{exam}-{topic} (or /guides/…)/ssc-cgl-syllabus
Search/search?q=…&body=…&age=…/search?q=graduate&age=21

Rules

  • Slug source of truth: stored on the row (slug), generated once, never silently changed.
  • Canonical + redirects: one canonical URL per entity; keep a redirect map for any slug change (301). Trailing-slash and case normalised at the edge.
  • Lowercase, hyphenated, ASCII; no dates-in-query for indexable pages; no session IDs.
  • Stable years: cycle URLs embed the year so last year’s page keeps its rankings and links.
Maps to your notesYour SEO page lists “URL Structure” first for a reason — it’s the spine the internal-linking and sitemap systems (§18) hang from.

Scrapers #

The scraper’s only job: reliably notice when an official source changes and capture a faithful snapshot. It does not interpret content — that’s the AI’s job (§6). Keeping scrape and understanding separate is what makes the “upgraded, AI-connected” scraper robust.

Architecture

Source registrysource table: URL, type, frequency, selectors, politeness
→
Schedulern8n cron per source / per body
→
Fetch workerPlaywright renders JS & PDFs
→
Change detectsha256 vs last_hash
→
Raw storeblob→Storage, row→raw_document

What good looks like

  • Source-typed parsers: a small adapter per source shape (SSC notice list, PDF notification, RSS, a state PSC page). parser_hint selects it.
  • Change detection first: hash the normalised content; only changed docs flow downstream → cheap, avoids re-processing.
  • Politeness & resilience: per-domain rate limits, randomised delays, retries with backoff, rotating user-agents/proxies, robots.txt respect, caching.
  • PDF-native: most notifications are PDFs — extract text layer, OCR fallback (Tesseract) for scans.
  • Observability: every run writes a scrape_run row (status, changed?, stats); dead sources alert.
Grey-hat guardrailScrape only public official pages, honour robots and rate limits, and cache aggressively. The goal is a respectful mirror of public information, with attribution — not a hammer.

Data Engine

AI Extraction #

The AI turns a messy notice or PDF into structured JSON that matches your schema. Use tool-use / structured-output so the model must return a valid object, not prose.

How it runs

  1. Classify the document: is this a new notification, a date change, an admit-card notice, a result, a cutoff PDF?
  2. Extract to a target schema (exam_cycle, key_date[], vacancy[], eligibility, official_link[]) with a confidence per field.
  3. Resolve entities: match to an existing exam/exam_cycle (fuzzy + rules) or propose a new one. This prevents duplicate “SSC CGL 2026” rows.
  4. Persist an extraction row (model, prompt_version, payload, confidence) linked to the raw doc.

Extraction contract (illustrative)

{
  "target_type": "exam_cycle",
  "match": { "exam_slug": "ssc-cgl", "year": 2026, "confidence": 0.97 },
  "fields": {
    "total_vacancy": { "value": 17727, "confidence": 0.93, "evidence": "para 2, notice PDF" },
    "key_dates": [
      { "label":"Last Date to Apply", "event_on":"2026-07-24", "confidence":0.95 }
    ]
  },
  "source_url": "https://ssc.gov.in/notice/cgl-2026.pdf"
}

Cost & quality controls

  • Cheap-first cascade: a small/cheap model does classification & simple fields; escalate to a stronger model only for hard docs.
  • Evidence spans: model cites where each value came from → makes validation & human review fast.
  • Prompt versioning: prompt_version stored per extraction so you can A/B and measure accuracy over time (see the eval harness in §20).

Validation Engine #

This is your “verifies the detail & sends report → score > 90% → publish” step, made concrete. It converts an extraction into a single 0–100 score with a breakdown and a human-readable report, then routes it.

The scoring pipeline

CheckTypeExampleWeight
Schema validRule (hard)Dates parse; vacancy is a number; required fields presentgate
SanityRuleEnd date ≥ start date; year matches; vacancy in plausible rangehigh
Source reachableRuleOfficial links resolve (HTTP 200) and are on official domainshigh
Cross-source agreementRuleTwo independent sources agree on the last datehigh
Model confidenceAIField-level confidence from §6medium
Consistency w/ historyAI“This year’s pattern vs last 3 cycles” — flags anomaliesmedium
Adversarial re-readAIA second model tries to refute the extraction from the same docmedium

Routing by score

≥ 90 · Auto-publishPasses all hard rules → straight to §9. Report archived.
70–89 · Human queueOne-tap approve/edit in a review inbox. <30s per item.
< 70 · RejectRe-queue with reason; may escalate model or flag source.

The validation row stores score, passed, the checks[] breakdown and a report string (this is the “report” your n8n step sends to Slack/Telegram/email). Human decisions are recorded (reviewed_by, reviewed_at) for audit and to build a training set.

Why this is the moatAnyone can scrape. Very few build a trustworthy gate. This engine is what lets you automate aggressively without ever betraying an aspirant with a wrong date.

Version Control #

Government dates change constantly (extensions, corrigenda). Versioning turns that churn into a feature: the “What’s changed” feed (F-12), safe rollback, and a full audit trail.

  • Snapshot per change: on every approved publish, write a content_version (full JSON snapshot + version_no).
  • Automatic diff: compute {field:[old,new]} vs the previous current version. e.g. {"last_date":["25 Aug","30 Aug"]}.
  • Feed generation: a meaningful diff auto-creates an update_feed row (“Last date extended to 30 Aug”) → homepage, dashboard, and notifications.
  • Rollback: flip is_current to a prior version if a bad extraction slips through — instant, non-destructive.
  • Audit: created_by (pipeline vs staff email) + link to the extraction/validation that produced it.
User-facing payoff“What changed since you last visited” and per-cycle changelogs build trust and bring people back — a retention loop powered entirely by data you already keep.

Publishing Engine #

Steps 3–5 of your flow: decide/arrange the data → feed it to the right page → page gets updated. The publisher takes an approved version and makes it live, correctly placed and instantly visible.

What it does

  1. Arrange / route: resolve the extraction to the exact target (which exam_cycle, which key_date) — create the exam/cycle if new, else update in place.
  2. Upsert + version: write content tables inside a transaction; snapshot a content_version; emit update_feed + fan out notifications (§17).
  3. Reveal: trigger Next.js on-demand revalidation for the affected paths (/ssc/cgl-2026, homepage, calendar) and purge the CDN. The page updates within seconds — no full redeploy.
  4. Confirm: write a publish_event (path, revalidated?) so publishing is itself auditable.

The n8n workflow (node-by-node)

# WF-1  Scrape (per source, on schedule)
Cron → HTTP/Playwright fetch → Hash → IF changed → Supabase insert raw_document → emit doc.id

# WF-2  Understand & gate (triggered by new raw_document)
Supabase trigger → AI Extract (structured) → insert extraction
   → Validation (rules + AI) → insert validation, compute score
   → IF score ≥ 90  → WF-3 (publish)
   → IF 70–89       → Review queue (Telegram/Slack approve buttons) → on approve → WF-3
   → ELSE           → mark rejected + notify ops

# WF-3  Publish (approved version)
Resolve target (exam/cycle) → Upsert content (txn) → Snapshot content_version + diff
   → Create update_feed → Fan-out notifications → POST /api/revalidate (Next.js)
   → Insert publish_event → done
Exactly your five stepsWF-2 = “verify & send report” + “score > 90 → publish”; WF-3 = “decide/arrange” → “feed to page” → “page updated”. n8n owns orchestration; Supabase is the state; Next.js renders.

Design System #

One visual language so every page feels like one product and new pages are cheap to build. Ship it as design tokens + a Tailwind config + a component library (§11).

Tokens

Color: a trustworthy blue primary, a warm saffron accent (a nod to the Indian civic palette, used sparingly), semantic green/amber/red for status. Type: Inter for Latin + Noto Sans Devanagari for Hindi. Spacing: 4-pt scale. Radius/shadow: soft, modern, calm.

Modes & a11y

Light + dark from day one (respect prefers-color-scheme). WCAG 2.1 AA contrast, full keyboard nav, visible focus, semantic HTML, 44px tap targets, reduced-motion support.

Bilingual-ready

Hindi + English are first-class. Keep copy in an i18n layer, avoid text-in-images, and pick fonts that render Devanagari cleanly. Huge for reach and SEO.

Performance budget

≤ 2.5s LCP on mid-range mobile, ≤ 150KB critical JS, system-ish fonts, lazy images, no layout shift (CLS < 0.1). Speed is a design principle here.

Status colors are shared across the app (they encode meaning, not decoration): Result Out Application Open Admit Card Closing Soon Completed Upcoming

Search #

Your “Smart Search” (F-7) is a headline feature: users type natural things like “age 21, B.A., all-India” and get matching exams. Deliver it in two layers.

Layer 1 — structured + full-text (ship first)

  • Query parser: split input into structured filters (age, qualification, body, state, level) and free text. “age=21” and “B.A.” become filters; the rest hits full-text.
  • Engine: Postgres FTS + pg_trgm (typo-tolerant) over the search_index materialised view; structured filters map to the eligibility engine.
  • Ranking: text relevance × freshness × status (open cycles first).

Layer 2 — natural language & semantic (upgrade)

  • A small LLM turns a free sentence into the structured filter object (“graduate exams I can give at 21 in MP” → {qualification:'graduate', age:21, state:'MP'}).
  • pgvector or Meilisearch/Typesense for instant, semantic, as-you-type results at scale.
Ties into the Eligibility Engine (F-3)Search and eligibility share one filter model, so “find exams I’m eligible for” is the same code path as the checker on the dashboard.

Notification Engine #

The retention flywheel. When the pipeline publishes a change, the right users hear about it — and only the relevant ones (your F-3 note: “Eligibility Engine → Notification (Relevant)”).

Launch #

Launch narrow and deep, not wide and thin. Own a few exam families completely before expanding.

Pre-launch checklist

  • Seed depth: 20–40 high-demand exams (SSC CGL/CHSL/MTS, a few state PSCs, IBPS, RRB) fully populated with real cycles, dates, vacancy, eligibility.
  • Accuracy audit: manually verify every seeded fact against the official source — day-one trust is everything.
  • SEO ready: sitemaps submitted, Search Console + analytics live, JSON-LD validated, canonical/robots checked.
  • Legal/trust: disclaimer + “not a government website” + official-source attribution on every page.
  • Perf: pass Core Web Vitals on mobile; test on a real budget Android + 3G.
  • Alerts: web push working end-to-end; a first “deadline reminder” demonstrably fires.

Rollout

Soft launch to a student community (one exam family) → gather corrections → tune the pipeline → widen exam coverage weekly. Let the automation prove itself on a small surface before you scale it.

Growth #

Growth here is a system, not a campaign — the same automation that keeps data fresh also produces the surfaces that acquire and retain.

Acquisition — SEO flywheel

Programmatic pages × freshness × schema. Every new cycle is a new fast, structured, internally-linked page. This is your cheapest, most durable channel.

Retention — the alert loop

Follows → relevant push/email → return visits → more follows. Deadline reminders are inherently sticky. “What’s changed” brings people back.

Virality — shareable tools

Compare pages, eligibility checker results, state map, and “days left” cards are made to be screenshotted and shared in coaching WhatsApp groups.

Monetization (later, tasteful)

Non-intrusive ads, a premium tier (advanced alerts, PYQ/test portal F-10, deep analytics), and coaching/affiliate partnerships. Never at the cost of trust.

SequencingNail acquisition (SEO) + retention (alerts) first. Virality and monetization compound once the data engine and audience exist — don’t rush them.
